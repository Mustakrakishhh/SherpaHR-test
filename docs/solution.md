# Обзор руководителя

Руководителю нужно увидеть проблемные задачи нескольких проектов, прочитать
контекст и сразу ответить или изменить задачу. На стартовом экране объединены
задачи всех исполнителей его активных проектов; существующие экраны сохранены.

## Сценарий

1. Выберите Анну: откроется «Требуют внимания».
2. Посмотрите причины и комментарии, при необходимости отфильтруйте причину.
3. Откройте задачу: доступны полная переписка, комментарий и редактор.
4. Чтобы явно попросить помощь, отметьте флажок у нового комментария. Руководитель
   увидит обращение даже без ключевых слов. Только руководитель проекта может
   отметить конкретную просьбу обработанной или вернуть её в обзор.
5. После отправки или сохранения обзор обновится. Завершённая задача исчезнет;
   снятая блокировка уберёт соответствующую причину. Карточка останется открытой.
6. В режиме «Все незавершённые» можно проверить задачи без выявленных сигналов.

Сортировка по ближайшему сроку, без срока — в конце, одинаковые сроки — по ID.
Фильтры не меняют порядок. Счётчики причин могут пересекаться: одна задача может
быть просрочена, заблокирована и одновременно содержать просьбу.

## Принятые правила

- «Мои проекты» в обзоре — проекты с текущим пользователем в роли руководителя
  (`owner_id`) и участника. Членство отдельно проверяется на сервере.
- Архивные проекты и готовые задачи исключены. Обычный список проектов продолжает
  показывать все доступные проекты и позволяет читать архив.
- Просрочка: срок строго раньше времени снимка API в UTC. Равенство не просрочка.
- Нет исполнителя: `assignee_id = null`, независимо от наличия срока.
- Явная просьба: флажок `help_requested` при отправке комментария. Её может создать
  любой участник активного проекта. Обрабатывает и возвращает только руководитель.
- В готовой задаче явный запрос помощи недоступен: UI отключает флажок, API
  возвращает 409. Обычные комментарии сохраняются. Снятие отметки старой просьбы
  не переоткрывает задачу; до ручного изменения статуса она не попадёт в обзор.
- Возможная просьба: совпадение одной из фраз во всей переписке незавершённой задачи:
  «нужна помощь руководителя», «нужна помощь», «помоги», «помогите»,
  «не можем продолжить», «нужно решение», «нужен ответ».
  Регистр и последовательности пробелов не учитываются; совпадают целые слова.
  Для контекста показан последний по ID необработанный подходящий комментарий
  и совпавшая фраза (либо признак явной просьбы).
  Если последний комментарий другой, он показан отдельно.
- Обработка относится к одному комментарию. Показывается число открытых обращений;
  после обработки последнего из них причина просьбы исчезает, а блокировка,
  просрочка и отсутствие исполнителя остаются. Новая просьба появляется независимо
  от старых отметок. История переписки сохраняется, отмена доступна в карточке.
- У отметки собственная версия: устаревшая вкладка получает конфликт 409.
- Ошибки действий из карточки показываются внутри неё. После отрисовки ошибка
  получает фокус и прокручивается в видимую область; поля, текст комментария и
  флажок сохраняются. При успешном завершении задачи флажок помощи снимается.
- Режим «Все незавершённые» нужен и для ручной проверки обсуждений: отсутствие
  найденного признака не означает отсутствие проблемы.
- Обновление при открытии обзора, вручную и после собственных изменений.
  Ошибка обновления явно помечает данные как потенциально устаревшие.

## Исправления и устройство

Удалён лишний inner join списка задач с пользователями: он скрывал задачи без
исполнителя. Восстановлена вставка комментария с автором из демо-контекста и
серверным временем. Версия полей задачи при комментарии не меняется.

Новый `GET /api/attention` собирает задачи и контекст на backend; логика находится
в `Attention.php`. Добавлена транзакционная миграция схемы 1→2: поля явной просьбы,
обработки и версии в комментариях. Имеющаяся БД обновляется автоматически, без
пересоздания задач, переписки и дат демо. Используются существующие
индексы, без отдельного запроса на каждую карточку. Новых внешних сервисов и
зависимостей нет. Карточка определяет участников и архивность по проекту открытой
задачи, а не по последнему выбранному экрану.

## Ограничения

- Поиск фраз не определяет смысл, отрицания, цитаты, адресата или факт решения
  проблемы. Старая возможная просьба остаётся сигналом до ручной обработки
  руководителем или завершения задачи. Другие формулировки можно явно отметить
  при отправке комментария; без флажка они могут быть пропущены.
- Нет фонового обновления, уведомлений и признака «прочитано».
  Сроки пересчитываются при следующем обновлении снимка.
- Сохраняется текущее состояние просьбы и автор/время её обработки, но отдельного
  журнала всех переключений состояния нет. «Обработано» — ручная отметка разбора,
  а не автоматическое подтверждение решения проблемы.
- Поиск в UI включает последний комментарий, но не всю переписку. Поиск признаков
  по фиксированным фразам, напротив, проверяет все комментарии.
- Для небольшого демо нет пагинации и полнотекстового индекса. При росте данных
  потребуются серверные фильтры/пагинация и отдельный индекс сигналов обсуждений.
- Исходные ограничения демо сохраняются: открытый переключатель пользователей,
  локальный PHP-сервер, UTC. Приложение не предназначено для публикации в сеть.

## Проверка

```bash
docker compose up --build -d --wait
docker compose exec -T app php backend/tests/smoke.php
docker compose exec -T app php backend/tests/migration.php
```

Сборка Docker включает production-сборку Angular. Smoke использует отдельную
временную БД: проверяет исходные операции, права, архив, конфликт версий,
комментарии, отбор и обновление обзора, Unicode-поиск фраз и границу просрочки,
явные просьбы, обработку/возврат, права и защиту от устаревшей отметки. Отдельный
тест миграции проверяет обновление БД версии 1 с пользовательскими данными.
Чек-лист воспроизведения исправленных дефектов: [regression-checks.md](regression-checks.md).
